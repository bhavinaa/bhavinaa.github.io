What CS3216 taught me about shipping fast

Product Reflection

CS3216 is built around one constraint: you ship a working product every few weeks, alone or in a small team, with real users trying it. That constraint changes how you think about everything — architecture decisions stop being abstract and start being "will this survive being touched by 50 people I've never met by Friday."

The lesson I didn't expect

I went in expecting to learn more about React patterns or backend architecture. What actually shifted was how I scope problems. The instinct to build the "correct" version of a feature is usually the wrong instinct when you have five days — the right question is what's the smallest version of this that tells us something true about whether users want it.

Ship something ugly that answers a real question before you ship something polished that answers a guess.

What I'd do differently

  • Instrument analytics on day one, not after the first user complaint — I lost a full week of signal on one project by adding tracking too late.
  • Write the one-paragraph pitch before writing code. If I can't explain why someone would use it in three sentences, the scope is still too vague.
  • Budget real time for the boring 20% — auth, empty states, error handling — because that's exactly what breaks demos.

None of this is groundbreaking advice. It's the kind of thing that's obvious in retrospect and easy to ignore in the moment, which is probably why it's worth writing down.
