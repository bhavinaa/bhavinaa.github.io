What I actually learned wiring up WebSockets in production

Engineering Real-time systems

Building the real-time multiplayer feature at Eduville was the first time I'd taken a WebSocket connection past "works on my machine." The happy path — client connects, sends events, server broadcasts — took an afternoon. Everything after that took two weeks.

Reconnection is the actual feature

In a live classroom, a student's laptop will drop wifi, a tab will get backgrounded, a school firewall will do something unexpected. None of that is an edge case — it's the median session. The real engineering problem wasn't "sync state live," it was "recover cleanly when the connection wasn't live for the last four seconds."

Things that actually mattered

  • Treating the client's state as recoverable, not authoritative — on reconnect, the client requests a fresh snapshot rather than trying to replay missed events.
  • Debouncing reconnect attempts so a flaky connection doesn't hammer the server with retries.
  • Making "who's currently connected" a first-class piece of state, not an assumption — teachers needed to see this accurately in real time.
The demo works because the network behaves. Production works because you assumed it wouldn't.

I went in thinking this was a WebSockets project. In hindsight it was a distributed-state problem that happened to use WebSockets as the transport.
